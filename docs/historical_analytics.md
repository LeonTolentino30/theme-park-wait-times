# Phase 5: Historical Wait Trends

The homepage adds a separate Historical Wait Trends section after Current Posted Waits. Select one of the seven approved active rides, choose the last 6 hours, 24 hours, or 7 days, and select **Show wait trends**. No request runs until submission. Reload/resubmit to include newly committed observations; no collector/provider polling process is added.

## Viewing the charts

Leave the collection terminal untouched. Only if the Flask website is already running, press Ctrl+C in its separate `app.py` terminal, then:

```powershell
# Open PowerShell in the repository root (the folder containing app.py).
.\venv\Scripts\python.exe -B app.py
```

Open http://127.0.0.1:5000/, reload the browser, and scroll to **Historical Wait Trends**. The website remains local-only with debug disabled. Do not stop or restart `src.collection_pilot` or terminate Python processes by name.

The chart is a responsive SVG generated by local JavaScript. No third-party charting package, CDN, paid service, dependency installation, or external network request is needed. Data points have timestamp/minute titles. A short list identifies closure/missing-wait/gap events. On small screens the chart scrolls horizontally to keep axis labels readable.

## Data semantics

All points come from successfully committed stored observation rows. The x-axis uses collection/fetch time, not provider last-change time. Requested bounds and actual first/last record times are displayed separately; unrecorded portions of the requested window stay empty. Axis labels, tooltips and event dates use America/New_York, including EST/EDT. API timestamps stay UTC.

Only present OPERATING observations with a nonnegative integer posted standby wait become numeric points. Genuine operating zero remains zero. CLOSED/DOWN/REFURBISHMENT/UNKNOWN/UNAVAILABLE and missing numeric waits are null points with events, never zero-minute waits. Inconsistent future provider timestamps are not used as numeric targets. Invalid records are never converted into estimates.

Straight lines connect adjacent numeric recorded samples only; they are not smoothed. A null record breaks the line. More than 450 seconds (7.5 minutes) between records also forces a break, allowing ordinary five-minute scheduling latency while exposing missed collection periods. Failed requests have no invented observation rows. No interpolation, forward-fill, generated waits or historical backfill occurs. Gaps can reflect sleep, outages, backoff, or park/provider availability; the chart does not infer their cause.

At least two distinct numeric observation times are required to draw a chart. Otherwise a clear insufficient-data message appears; any available closure/missing-wait events can still be shown. A short pilot window does not establish seasonal patterns or forecasting accuracy. These are **historical posted standby waits**, not measured actual time spent queuing and not AI forecasts. The synthetic predictor and current-waits dashboard retain their existing behavior.

## Read-only API

`GET /api/history?attraction_id=<approved UUID>&hours=6`

`hours` accepts exactly `6`, `24`, or `168` (default `24`). Alternatively supply both `start` and `end` ISO 8601 timestamps with explicit timezone offsets, without `hours`. URL-encode `+` offsets when constructing a query manually. An explicit range must increase, span no more than seven days, and end no later than now. Its results are limited to actual available records; no points are invented at the endpoints. Missing/unknown attractions, retired IDs, duplicate/unknown parameters, invalid hours and invalid date ranges return meaningful HTTP 400 JSON errors.

Responses include attraction/park, requested and observed periods, recorded `points`, numeric count, chart readiness, gap threshold, source attribution and interpretation disclaimer. Every point carries collection time, posted wait or null, status, event and gap-break metadata. No database paths, raw response BLOBs, logs or error strings are returned.

Queries use an existing SQLite file with `mode=ro`, connection-local `query_only`, a short consistent read transaction and a 250 ms lock timeout. Selected rows are materialized before processing and the connection closes immediately. No schema/index changes or checkpoints occur. Reads work alongside the collector's WAL writer. A seven-day window is bounded to 2,500 rows per attraction; an unexpected excess fails safely rather than silently truncating/sampling data. Missing/corrupt/busy databases or unavailable mappings return sanitized HTTP 503; an available database with no matching observations returns 200 with an insufficient-data message. A missing database is never created.

This endpoint exists for the local app's chart, not as a public provider feed, bulk download or data export. Observations and the database remain under Git-ignored private storage.
